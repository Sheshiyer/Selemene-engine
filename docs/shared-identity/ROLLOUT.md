# Shared identity staging rollout

The migration connection and API runtime connection are different authorities. Never deploy the shared reader with a superuser or BYPASSRLS `DATABASE_URL`. Shared account handlers reject privileged connections in production, or whenever `NOESIS_REQUIRE_BOUNDED_DB_ROLE=true`.

1. Compare the hosted journal through 044 with the checked-in immutable checksums. Use the existing migration principal to run `scripts/apply-migrations.sh --migrations-dir migrations -- <private psql connection arguments>`. This is a separate release operation; do not put its credential in the API service. The container starts the server directly and does not require the migration credential at runtime.
2. With that migration principal, run `scripts/identity/provision-runtime-role.sql`. It creates `noesis_api_runtime` with LOGIN, NOSUPERUSER, NOBYPASSRLS, NOCREATEDB, NOCREATEROLE, NOREPLICATION and NOINHERIT. It grants existing legacy/public-table DML and sequence usage while excluding writes to the migration journal; it grants no schema CREATE, ownership or role membership. The script stops if inherited PUBLIC schema CREATE privileges or unexpected membership/ownership would weaken the boundary. Inspect and separately authorize any DB-wide PUBLIC privilege hardening; the script does not silently change other principals.
3. Set a strong runtime password privately using `\password noesis_api_runtime` or the deployment secret manager. Set API `DATABASE_URL` to this role; retain migration access only in the release/operator context. Never publish the credential. Repeat the privilege grant step after future migrations introduce new tables.
4. Read back `current_user`, `rolsuper`, `rolbypassrls`, schema CREATE privilege and role memberships using the exact runtime credential. The runtime must not own tables or hold a membership allowing `SET ROLE` into the migration principal. Audit any unexpected SECURITY DEFINER functions in public before deployment. Root migrations in this change introduce none.
5. Configure `NOESIS_REQUIRE_BOUNDED_DB_ROLE=true`, `NOESIS_ACCOUNT_ORIGIN` to the exact HTTPS API origin without trailing slash, the separate end-user CF issuer/audience, and exact client redirect allowlists. The browser POST Origin is the API origin where the verification page is open, not the Daily origin. End-user Access must cover sessions/authorize, email-links/begin, email-links/verify and email-links/complete. Token/revoke endpoints remain reachable for possession-bound PKCE/refresh exchanges.
6. Deploy staging first. Verify account context, missing grants, subject profile CAS, enrollment through registered human sessions, logout/revocation, independent relationship grants and Witness head CAS using the actual runtime credential. Test direct SQL reads on a borrowed runtime connection without account context: private profile/run/catalog rows must be invisible. Check transaction-local context resets after commit/rollback. A health response alone does not prove these checks.
7. Verify real browser source-account binding and new-email proof, then real callback and cross-surface readback before production. Preserve the private-reader rollback; do not restore exposed static assets or privileged runtime credentials as a fallback.

## Email browser flow

The initial authenticated POST `/account/email-links` returns the same response shape, with `verification_path` now `/api/v1/account/email-links/begin?challenge=...`. GET renders only. The source-account confirmation button makes a same-origin POST to `/begin`; a fresh provider assertion must map to the initiating account. Only then does the server bind a digest of an HttpOnly Secure SameSite=Strict browser nonce to the challenge and return the `/verify` page link. The user switches to the requested email through the identity provider. GET `/verify` also renders only. Its explicit confirmation POST `/complete` requires the source-bound cookie, exact Origin, `confirm:true`, an unexpired challenge and a fresh proof for the requested email. A victim opening an attacker's challenge URL cannot establish source-account proof or complete the link. Original login email and UUID remain stable; successful completion revokes registered sessions and requires sign-in again.

## Private bootstrap mapping

There is no general resource-import API in this change. Use a separately reviewed private, journaled SQL transaction with the migration/operator principal for the initial three accepted source profiles. Do not commit the seed payload, identities, birth facts or credentials to this repository.

- Lock and resolve the existing approved account by its exact verified provider identity/explicit account UUID; check normalized-email ambiguity rather than assuming a name identifies it.
- Allocate explicit new subject UUIDs and owner-scoped stable keys. Assert absence of each `(owner_user_id,subject_key)` before insertion. Preserve unrelated existing corpus subjects; never merge by display name or birth date.
- Insert the reviewed profile revision 1 values with source hashes and canonical serialized profile checksum; record exact source/profile hashes and resource UUIDs in the private operator receipt. Initial import is an explicit privileged operation, not an ordinary read-only owner PATCH.
- Bind only the already verified owner's self subject. Grant own read/edit/calculate and explicit read/calculation grants for the other approved subjects without edit. Leave recipient self links absent until verified enrollment and owner confirmation establish them.
- Create the pair and its subject-member rows using composite owner references. Grant the verified owner relationship read. Include the explicit pair UUID in the appropriate recipient invitation `relationship_ids`. Verified acceptance/owner confirmation grants only that pinned pair; invitations for nonmember subjects are rejected. Subject membership alone never grants pair access.
- Set the verified owner's default subject. Persist recipient defaults only after their verified account bindings exist.
- Commit the bootstrap and private audit atomically. Keep an operator-private schema/journal outside public runtime grants, or an authenticated private receipt containing only identifiers/hashes. Reruns must compare the exact prior receipt and expected rows, not silently `ON CONFLICT UPDATE` private source/profile data.

No production migration, credential change or bootstrap is performed by this runbook itself.
