### Interpretation

- **Vara (100%) and paksha (100%)** validate end-to-end timezone parsing and
  the Shukla/Krishna split — the engine's date arithmetic against the
  reference's numeric IST offset is solid.
- **Tithi name (50%)** drifts by ±1 index on three of six points. Combined
  with `tithi_number` drifting in the same direction, this points at the
  Sun–Moon longitude separation being slightly off — likely an ayanamsa
  precision issue (the engine uses a constant 23.72° Lahiri shift; the
  reference uses the cross-verified Lahiri/Chitrapaksha value).
- **Yoga (0%)** is the standout regression. Yoga depends on the Sun+Moon
  longitudinal sum; the consistent miss across all six fixtures is a stronger
  symptom of the ayanamsa/longitude issue than tithi.
- **Nakshatra pada (16.7%)** drifts by 1 pada on all but one fixture, which
  again is consistent with sub-degree lunar longitude drift (3°20′ per pada).

The harness is doing exactly what it was designed for: surfacing real
sub-degree numerical drift between the engine and the JHora reference.

```
  chart_2_modern_reference   expected=Saturn,Mercury,Ketu,Venus
                             got=Venus,Sun,Moon,Mars
  chart_3_ketu_birth_dasha   expected=Ketu,Venus,Sun,Moon
                             got=Moon,Mars,Rahu,Jupiter

mahadasha_start_date_15d (8 mismatches, examples):
  shesh_1990_bangalore/md2          expected=1999-01-15 got=1993-05-12 diff=2074d
  chart_1_swami_vivekananda/md2     expected=1866-06-29 got=1868-08-12 diff=775d
  chart_2_modern_reference/md3      expected=2016-07-15 got=2002-09-19 diff=5048d
  chart_3_ketu_birth_dasha/md3      expected=2024-03-01 got=2010-09-26 diff=4905d
```

### Interpretation

- **Only the Shesh chart matches** across nakshatra, birth-dasha-planet, and
  mahadasha sequence (the engine returns Mercury / Revati and the right
  sequence). All 3 charts from `dasha_reference.json` miss the nakshatra,
  which means the upstream Moon-longitude computation lands the Moon in a
  *different nakshatra* for those 3 birth times — usually a 1-2 nakshatra
  drift (≈13-27°), which is much larger than the ±0.01° ayanamsa drift
  diagnosed for panchanga.
- The `birth_dasha_balance_years` is consistently *under*-stated by the
  engine for charts whose true birth dasha is *not* the one the engine
  picked. That's mechanically downstream of getting the wrong starting
  nakshatra → wrong starting planet → wrong remaining-fraction.
- Mahadasha start dates drift by years (often 2000+ days), which is the
  expected consequence of starting from the wrong dasha balance.

The most likely root cause is the Moon-longitude path inside
`engine-vimshottari` (it uses `engine_human_design::ephemeris::EphemerisCalculator`
and then applies `Self::to_sidereal_longitude`). The Shesh chart's correct
behaviour suggests the path *can* land correctly; the question for follow-up
is whether the three failing charts hit a different code branch (e.g.
mode-2 moon_longitude vs mode-1 birth_data) or whether the sidereal
conversion has historic-date drift the JHora references don't.

Recommended Phase-2 investigation: dump the engine's intermediate
`sidereal_moon_longitude` for each of the four charts and compare against
the references' `moon_data.moon_longitude` directly. The current harness
already has the hooks to extend.

## What we are NOT claiming

- These results are **not** "the engine is broken." They are the first
  ground-truth-anchored numbers for the Vedic engine stack. The Vedic
  numerical drift surfaced here is the *artifact this PR exists to expose*.
- The harness is **not exhaustive**: 6 panchang points + 4 dasha charts is
  enough to bootstrap the per-field pipeline; it is not a per-person sweep.
  Phase-2 must extend the reference set (see PR4 commit 6 follow-ups).
- These numbers are **not** comparable to humdes/HD validation accuracy.
  Different engines, different ground truth, different domain.
